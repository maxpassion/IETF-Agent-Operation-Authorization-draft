Delegation Chain for OAuth 2.0

Abstract

RFC 8693 defines the act claim for multi-hop actor identification in JWTs but does not record per-hop authorization constraints or provide delegator cryptographic confirmation. This specification defines the delegation_chain JWT claim as a structured companion to act: an ordered array of delegation records capturing the authorization constraints delegated at each hop (expressed as scope, with an opaque reference for deployments that use structured authorization constraints), each record carrying the delegating agent's cryptographic confirmation. The companion root_authorization_ref claim references the original user authorization from which the chain derives. act and delegation_chain together provide runtime authorization and verifiable delegation lineage. The specification defines the validation rules a Resource Server applies to the chain, the Token Exchange flow through which chains are extended, and how a chain crosses trust domain boundaries with the JWT authorization grant of OAuth identity chaining, in which each record additionally carries the attestation of the Authorization Server that created it.¶

1. Introduction

In multi-agent systems, a primary agent (Agent A) may need to delegate a subset of its authorized operations to a secondary agent (Agent B), which may in turn delegate further to Agent C. Each delegation hop must preserve the original user's authorization intent while constraining what each downstream agent is permitted to do.¶

OAuth 2.0 already provides building blocks for expressing delegation. RFC 8693 defines the act claim, which supports nested multi-hop actor identification (enabling a token to express that Agent A delegated to Agent B, which in turn delegated to Agent C). [I-D.ietf-oauth-identity-chaining] defines the cross-domain transport pattern combining Token Exchange ([RFC8693]) and JWT Authorization Grant ([RFC7523]) to carry identity and authorization information across trust domain boundaries. These mechanisms address the runtime side of delegation: who is currently acting, and how to move tokens across domains.¶

However, two structural gaps remain for agent delegation scenarios:¶

  • Per-hop authorization constraints: The act claim identifies the actors at each hop but does not record what authorization constraints were applied at each delegation step. A downstream Resource Server sees the final scope but cannot verify whether intermediate agents narrowed or expanded the authorization along the way.¶
  • Delegator cryptographic confirmation: The act claim is constructed unilaterally by the Authorization Server. The delegating agent leaves no independent cryptographic evidence that it authorized a specific delegation. This limits non-repudiation and post-hoc audit capabilities.¶

This specification introduces the delegation_chain claim as a structured companion to act. While act provides runtime actor identification for authorization decisions, delegation_chain records the full delegation history as an ordered array of delegation records. Each record captures the authorization constraints delegated at that hop and carries the delegator's cryptographic confirmation, so that neither the Authorization Server nor any delegating agent can unilaterally construct or deny a delegation record. The token also carries a root_authorization_ref claim referencing the original user authorization from which the chain derives, so that downstream verifiers can check that no hop exceeds it. The claims coexist in the same token: act identifies the current actor for the Resource Server, and delegation_chain records how the authorization was delegated, step by step, for verification and compliance systems.¶

The delegation_chain claim addresses delegation lineage and verification, complementing the runtime semantics provided by existing OAuth mechanisms. Cross-domain delegation (Section 7) addresses the multi-domain scenario. This version of the specification focuses on linear delegation chains; other complex topologies such as diamond-shaped delegation, where multiple paths converge on the same agent, may be addressed by future extensions.¶

Scope Boundary: This specification addresses problems that lie outside the design scope of Token Exchange ([RFC8693]) and Identity Chaining ([I-D.ietf-oauth-identity-chaining]). Token Exchange defines how to convert one token into another but does not record the delegation lineage across multiple hops. Identity Chaining defines how to transport identity across trust domains but intentionally leaves Claims Transcription representation undefined. The two problems addressed by this specification, multi-hop delegation lineage and delegator non-repudiation, are separate from both token conversion and cross-domain transport. Merging this mechanism into either existing specification would broaden its scope beyond its original design intent and impose delegation lineage complexity on deployments that do not need it.¶

This specification defines the delegation lineage mechanism. The structure of delegated authorization constraints, when carried by reference, is deployment-specific and out of scope of this specification; the consent lifecycle and evidence model belong to separate work.¶

Relationship to Compositional Approaches: [I-D.klrc-aiagent-auth] composes existing OAuth mechanisms (Token Exchange, Transaction Tokens, and CIBA) to address agent authentication and authorization. Composition of existing mechanisms alone does not provide per-hop delegator cryptographic confirmation or a verifiable delegation history; that is the layer this specification defines. The two approaches can be used together: compositional frameworks provide the transport and runtime semantics, and delegation_chain provides the structured delegation record and non-repudiation layer.¶

Relationship to Cross-App Access (ID-JAG): The Identity Assertion JWT Authorization Grant (ID-JAG) ([I-D.ietf-oauth-identity-assertion-authz-grant]) profiles Identity Chaining for Cross-App Access (XAA): an application obtains an access token for a third-party API by presenting an identity assertion brokered through the IdP that the downstream Resource Authorization Server already trusts for single sign-on and subject resolution. ID-JAG addresses the identity side of that exchange; its AI agent use case covers a single agent acting as an OAuth client of external tools on behalf of a user. The specification itself marks what it leaves open on the delegation side: it "does not define normative processing requirements for actor_token or whether an act claim is included in the issued ID-JAG", and, beyond requiring that the same ID-JAG not be reused for a different downstream Resource Authorization Server, it leaves propagation across additional downstream hops to "other mechanisms" that "MAY be used", without defining how authorization propagates and narrows along the way.¶

This specification defines such a mechanism, and the mapping to the gaps above is direct. For the actor delegation that ID-JAG defers to future extensions, this specification defines the delegation record, the delegator's per-hop cryptographic confirmation, and the rules for constructing act when delegation_chain is present (Section 2.1). For the downstream-hop gap, the delegation_chain claim carries the per-hop scope and constraint lineage that a downstream Resource Server verifies (Section 8), independently of the IdPs that resolved the subjects at each boundary. For the single-agent use case, the wit:// and spiffe:// agent identifiers (Section 3) extend the model to agent-to-agent delegation. The two specifications compose at the root authorization: an AS MAY verify the user's identity for the first delegation using an identity assertion grant (Section 4.4), after which delegation_chain records how authorization flowed from that root to the token presenter. ID-JAG resolves who the subject is at a trust boundary; delegation_chain records how the authorization was delegated from that subject.¶

2. Relationship to Existing Mechanisms

This section describes how the delegation_chain claim relates to existing OAuth 2.0 mechanisms, establishing the precise boundary between runtime delegation semantics and structured delegation records.¶

2.1. Relationship to the act Claim

RFC 8693 defines the act claim to express that delegation has occurred and to identify the acting party. The act claim supports nested multi-hop actor chains: a token can express that Agent A delegated to Agent B, which delegated to Agent C, all within a single nested JSON structure. This nesting enables Resource Servers to identify the current actor and trace the actor lineage for authorization decisions.¶

The act claim is constructed by the Authorization Server alone: the AS assembles the nested actor chain without requiring independent proof from each delegating agent. This is sufficient for runtime authorization decisions but does not capture per-hop policy constraints or delegator consent.¶

These properties cannot be added to act itself. The act claim carries no authorization content: it records who acted on whose behalf, but not what authorization was granted at each hop. Its processing model, as defined by [RFC8693], is an AS-attested identity statement: an implementation that understands act validates the actor chain as issued by the Authorization Server and would ignore additional members carrying per-hop signatures or constraints, silently accepting a token whose delegation evidence it did not check. Defining per-hop evidence inside act would therefore change the meaning of an existing, deployed claim, which is a matter for the base specification rather than for an extension. The delegation lineage is consequently defined as a separate claim, and act retains its RFC 8693 semantics unchanged.¶

The delegation_chain claim complements act by recording the delegation lineage as a structured array of records. Each record captures the authorization constraints applied at that hop (scope, and, when present, policy_ref) and the delegator's own cryptographic proof (delegator_signature), which is REQUIRED on every record. Records created by an Authorization Server other than the issuer of the token carrying the chain additionally carry that AS's attestation (as_signature). This enables:¶

  • Per-hop policy constraints: Each delegation record carries the authorization applied at that hop, not just the final scope. This preserves the full delegation lineage and enables scope narrowing verification.¶
  • Delegator proof: The delegator_signature on each record provides independent evidence of each delegator's consent, enabling non-repudiation that the AS alone cannot provide.¶
  • Root authorization reference: The root_authorization_ref claim references the original user authorization, enabling downstream verifiers to check that no hop exceeds it.¶

A token that carries delegation_chain MAY also carry a flat act claim for compatibility with Resource Servers that implement [RFC8693]. In a token carrying both claims, act identifies the current actor for the Resource Server's authorization decision, while delegation_chain provides the structured delegation record from the current actor back to the original human principal. The delegatee_id of the most recent delegation record (index 0) MUST match the act.sub value, ensuring continuity between the two claims. The current delegatee is identified by delegation_chain record 0 whether or not act is present.¶

[RFC8693], Section 4.4, expresses multi-hop delegation by nesting act claims within one another, the least recent actor being the most deeply nested. This specification defines a different representation for tokens carrying the delegation_chain claim: in such tokens the act claim contains a single sub value (the current delegatee) and MUST NOT contain a nested act claim. The actor lineage is conveyed by the delegation_chain array instead of nested act claims, so that it is independently verifiable and carries per-hop constraints. Authorization Servers MUST NOT nest act claims in tokens that carry delegation_chain, and Resource Servers MUST NOT expect nested act claims in such tokens. delegation_chain is thus a companion claim that reuses act for current-actor identification while taking over the multi-hop lineage role of nested act claims with a separately verifiable structure.¶

[RFC8693], Section 4.1, defines the may_act claim, which states that one party is authorized to become the actor and act on behalf of another party. may_act and delegation_chain are complementary: an Authorization Server MAY use may_act in an issued token to pre-authorize specific delegatees for a subsequent delegation hop, in which case a delegation request naming a delegatee matching may_act is a candidate for authorization without further permission checks. The delegation_chain record then captures the hop that may_act enabled. Whether a given delegation is permitted is determined by AS policy, expressed through may_act, a delegation scope, or other deployment-specific means; this specification defines how a permitted delegation is represented and validated.¶

2.2. Relationship to Identity Chaining

[I-D.ietf-oauth-identity-chaining] defines a general-purpose pattern for preserving identity and authorization information across trust domains, combining Token Exchange ([RFC8693]) and JWT Authorization Grant ([RFC7523]). It addresses the transport side of cross-domain delegation: how to move a token from Domain A to Domain B while preserving the user identity and authorization context.¶

This specification reuses the identity chaining transport for cross-domain delegation (Section 7) and adds agent-specific extensions:¶

  • delegation_chain claim: An explicit, cryptographically signed delegation record of all delegation hops, which identity chaining does not define;¶
  • Constraint narrowing enforcement: Each delegation hop carries a scope equal to or narrower than its predecessor; structured constraints (policy_ref) are attested by the issuing AS when present;¶
  • Per-hop signatures: The delegating agent signs each delegation record, and records that cross a domain boundary additionally carry the creating AS's attestation, preventing unilateral forgery;¶
  • Agent Identifier URIs: Resolvable URI-based identity for delegators and delegatees, supporting WIT and SPIFFE schemes.¶

The two differ in deployment scope: identity chaining addresses general cross-domain identity propagation (human users, CI/CD pipelines, SSO extension), while this specification profiles that transport specifically for agent-to-agent delegation with delegation lineage requirements.¶

2.3. Relationship to Claims Transcription

Section 2.5 of [I-D.ietf-oauth-identity-chaining] defines Claims Transcription (the process by which Authorization Servers add, change, or remove claims when producing JWT authorization grants or access tokens during cross-domain flows). That specification explicitly leaves the representation of transcribed claims undefined: "The representation of transcribed claims and their format is not defined in this specification."¶

The delegation_chain claim provides one such representation. When delegation crosses a trust domain boundary, each delegation record captures the transcribed authorization constraints (scope, and when present policy_ref) and the cryptographic evidence of the transcribing parties (the delegator via delegator_signature, and the AS that created the record via as_signature). This enables the receiving domain to verify what was transcribed, who authorized the transcription, and under what constraints, which addresses the representation gap left by identity chaining.¶

Implementations using identity chaining for cross-domain delegation SHOULD include the delegation_chain claim in the JWT authorization grant as a structured Claims Transcription format, enabling the receiving AS to validate the delegation lineage before issuing a local access token.¶

2.4. Relationship to Refresh Tokens and Async Refresh

This specification builds on refresh tokens ([RFC6749]); it does not replace them. A refresh token expresses a 1:1 relationship between a client and an Authorization Server: when it is used, the AS re-evaluates and issues a new access token, but the refresh exchange itself carries no record of who authorized what, at which hop, under which constraints. A delegation_chain records exactly that: an N-hop lineage in which each hop carries its own authorization constraints, signatures, and evidence anchor, with scope narrowing propagated along the chain. The two compose: refresh tokens remain the mechanism through which a client obtains fresh access tokens, and the delegation_chain in the issued token preserves the delegation lineage across those refreshes. Concretely, when an Authorization Server issues a new access token in a refresh exchange for a delegated token, it MUST carry the delegation_chain of the refreshed token unchanged: a refresh is not a delegation event and MUST NOT prepend, modify, or drop records.¶

The asynchronous refresh problem for delegation chains, in which a chained token expires while the user is offline and an agent must refresh it without widening privileges, breaking the identity chain, or impersonating the user, is addressed by Delegated Refresh Tokens for OAuth 2.0 Token Exchange ([I-D.zhu-oauth-async-delegation]). That specification defines the refresh of delegation chains; this specification defines the chain structure that is being refreshed. The two are complementary and can be combined.¶

3. Terminology

Delegator:
An agent that transfers a subset of its authorization to another agent.¶
Delegatee:
An agent that receives delegated authorization from a delegator.¶
Delegation Hop:
A single transfer of authorization from one agent to another.¶
Delegation Chain:
An ordered sequence of delegation hops from the most recent back to the original authorization.¶
Root Authorization:
The original authorization granted by a human principal, from which all delegations derive.¶
Workload Identity Token (WIT):
A token that cryptographically attests to the identity of a workload or agent, typically issued by a workload identity provider. A WIT URI is a URI that identifies a specific agent and references the WIT bound to that agent's identity.¶
Agent Identifier:
A URI used to identify a delegating or delegatee agent in a delegation record. This specification defines two URI schemes for agent identifiers: WIT URIs (wit://) and SPIFFE IDs (spiffe://). The identifier MUST be resolvable to a verifiable public key for signature verification.¶

The root_authorization_ref claim is an opaque identifier referencing the root authorization event: the original authorization granted by the human principal from which all delegations in the chain derive. It MUST be present in every access token that carries a delegation_chain claim. The chain records how authorization was delegated between agents; the root authorization itself is not recorded as a chain entry, because the delegator of every chain record is an agent with a resolvable key, whereas the root authorization originates from the human principal through the initial OAuth flow. The root_authorization_ref claim is the pointer that anchors the chain to that origin.¶

The format of the identifier and the mechanism for resolving it are deployment-specific: deployments using a structured authorization evidence model SHOULD set this value to the identifier of the root token's evidence claim; other deployments MAY use any stable, unique identifier (e.g., a consent record ID or an audit log entry reference) that enables post-hoc retrieval of the original authorization context. This specification treats the value as opaque. When the AS issues a delegated token, it propagates the root_authorization_ref claim from the subject token, and the receiving AS of a cross-domain flow propagates it from the JWT authorization grant, so that every token in the lineage anchors to the same root authorization.¶

4.4. Delegation Lifecycle

A delegation record transitions through three phases during its lifecycle:¶

  1. Delegation Proposal Phase: The delegating agent creates a delegation proposal that includes the delegatee identity, the delegated scope, and, when structured constraints are used, a reference to them, and signs the prospective record with the key that its delegator_id resolves to.¶
  2. Delegation Enforcement Phase: The Authorization Server validates the delegation request, verifies the delegator's token, verifies the delegator's signature on the delegation_proposal, and issues the delegation record upon successful validation. For the first delegation (User to Agent A), the AS MAY additionally verify the user's identity using an identity assertion grant ([I-D.ietf-oauth-identity-assertion-authz-grant]).¶
  3. Chain Propagation Phase: The delegation record is embedded into an access token's delegation_chain claim, enabling multi-hop propagation within or across trust domains.¶

This three-phase model cryptographically binds the root authorization reference, agent identities, and policy constraints at every hop. Whether the Authorization Server requires user consent before authorizing a delegation hop is AS policy and is out of scope of this specification; the mechanism for obtaining such consent, when required, is likewise out of scope.¶

4.5. Field Definitions

Table 1: delegation_chain Record Fields
Field Type Requirement Description
delegator_id string REQUIRED A URI identifying the delegating agent. This specification defines two URI schemes: wit:// (WIT URI) and spiffe:// (SPIFFE ID). The URI MUST be resolvable to a verifiable public key for delegator_signature verification.
delegatee_id string REQUIRED A URI identifying the receiving agent. The same URI scheme considerations as delegator_id apply.
delegation_timestamp NumericDate REQUIRED When this delegation was authorized.
scope string CONDITIONAL The delegated scope at this hop, expressed as a space-delimited list of scope values ([RFC6749], Section 3.3). REQUIRED when the chain contains more than one record, so that scope narrowing along the chain is verifiable by any holder of the token; MAY be omitted on single-record chains, where the delegated scope is conveyed by the access token's scope claim. When present, this field captures the scope explicitly authorized at this hop and is included in the signature computation to prevent scope expansion by a compromised AS. The Resource Server verifies that scope narrows monotonically along the chain (Section 8).
policy_ref string OPTIONAL An opaque reference to the structured authorization constraints that apply to this delegation hop, for deployments that use a structured constraint model. The format and resolution mechanism of the reference are deployment-specific; this specification treats the value as opaque (the same treatment as root_authorization_ref). The referenced constraints MUST NOT expand the delegator's authorization; this is enforced by the Authorization Server at issuance time and attested by the record's signatures. When absent, the delegated constraints are expressed solely by scope.
delegator_signature string REQUIRED Cryptographic signature from the delegating agent's private key over this delegation record. Every delegation record MUST carry this field: it provides independent evidence that the delegator authorized this specific delegation, which the Authorization Server alone cannot attest, and enables non-repudiation. Because the field is REQUIRED, its absence is unambiguous evidence of an invalid record rather than a deployment choice. The signature uses the private key that the record's delegator_id resolves to (see the Key Resolution section of this specification).
as_id string CONDITIONAL An identifier for the Authorization Server that created this delegation record. REQUIRED when as_signature is present, where it identifies the issuer of that signature and enables the verifier to select the correct public key. In single-domain chains where as_signature is omitted, the token's iss claim already identifies the creating AS and this field MAY be omitted.
as_signature string CONDITIONAL Signature of the Authorization Server that created this record, over the same field set as delegator_signature. REQUIRED when the record was created by an AS other than the issuer of the token carrying the chain (cross-domain chains), so that the receiving domain can independently verify each foreign hop and hold the creating AS accountable for it. When the record's AS is the token's issuer, the token's own signature already attests to the record and this field MAY be omitted.

The authorization constraints delegated at a hop are expressed as scope: this is the baseline form, REQUIRED whenever the chain contains more than one record so that scope narrowing along the chain is verifiable by any holder of the token. Deployments that use a structured constraint model additionally carry policy_ref, an opaque reference to the approved constraints. This specification does not define the format, resolution, or comparison of the referenced constraints; narrowing with respect to the delegator's authorization is enforced by the Authorization Server at issuance time (Section 5.1) and attested by the record's signatures.¶

The delegation_timestamp MUST satisfy the following constraints:¶

  • It MUST be less than or equal to the access token's iat (issued at) claim, since the delegation event occurs before or at the time the token is issued;¶
  • It MUST be greater than or equal to the delegation_timestamp of the temporally earlier delegation record (the record at the next higher array index), ensuring that timestamps are monotonically non-increasing from index 0 (most recent) to index N (earliest). When the two records were signed by different Authorization Servers (cross-domain chains), this comparison SHOULD tolerate clock skew between the two AS instances, consistent with the freshness window below; a small negative delta between independently clocked hops is not by itself evidence of an invalid chain.¶
  • It MUST be within the validity period of the delegator's token at the time of the delegation request (i.e., greater than or equal to the delegator token's iat and less than or equal to the delegator token's exp).¶
  • At the time the AS processes the delegation request, the timestamp SHOULD be within an acceptable freshness window relative to the AS's current time. A RECOMMENDED maximum skew is 5 minutes in either direction. Timestamps outside this window SHOULD be rejected to mitigate replay attacks (see Section 9).¶

The delegator_signature and, when present, the as_signature MUST be computed over the same set of fields. The signature is a JWS ([RFC7515]) compact serialization. The JWS payload is a JSON object containing exactly the following fields (omitting OPTIONAL fields that are absent); the payload SHOULD be serialized using the JSON Canonicalization Scheme ([RFC8785]) so that the same set of fields deterministically produces the same bytes across implementations:¶

  • delegator_id¶
  • delegatee_id¶
  • as_id¶
  • delegation_timestamp¶
  • scope (if present)¶
  • policy_ref (if present)¶

Both signature fields MUST be excluded from their respective signature computations. The JWS alg header MUST be set appropriately (e.g., RS256 for AS signatures, ES256 for delegator signatures). The JWS kid header SHOULD be included to facilitate key resolution. The resulting compact JWS string is stored as the value of the respective signature field. When verifying, the verifier decodes the JWS payload and confirms that the decoded JSON object matches the delegation record fields.¶

The two signatures serve distinct purposes. The delegator_signature, which is REQUIRED on every record, uses the delegating agent's agent-identifier-bound private key and provides:¶

  • Malicious AS Prevention: A compromised AS cannot unilaterally forge delegations without the delegator's consent;¶
  • Non-Repudiation: The delegator cannot deny having authorized the delegation.¶

The as_signature uses the creating Authorization Server's signing key. It is REQUIRED only on records created by an AS other than the token's issuer: in single-domain chains, the token-level signature of the issuing AS attests to every record in the chain, so per-record as_signature would duplicate that attestation. In cross-domain chains, it provides the originating AS's witness attestation for each foreign hop, enabling the receiving domain to verify that hop independently of the transcribing AS.¶

4.6. Key Resolution for Agent Identifiers

Verification of the delegator_signature (and of the delegatee's key binding) requires the relying party to resolve the agent identifier to a verifiable public key. The resolution mechanism depends on the URI scheme used in the delegator_id or delegatee_id field:¶

The wit:// scheme used in the examples of this specification has the following syntax:¶

The authority component identifies the workload identity provider or trust domain (for example, wit://agent-a.example). The first path segment is the agent identifier, conventionally a digest of the agent's public key prefixed by the hash algorithm, for example, wit://agent-a.example/sha256.aaa111...: once the relying party has resolved the authority to a trusted provider, the identifier itself determines which key material it names. Deployments MAY use other agent identifier forms within the same scheme, provided the deployment documents how the identifier resolves to a key. SPIFFE IDs are used with their usual semantics.¶

  • wit://: The WIT URI is resolved via the workload identity provider's attestation bundle, which contains or references the agent's public key (e.g., via SPIFFE bundle endpoints);¶
  • spiffe://: The SPIFFE ID is resolved via the SPIFFE Bundle Endpoint protocol, which provides the agent's X.509-SVID or JWT-SVID containing the public key.¶

Implementations SHOULD document the supported URI schemes and their resolution mechanisms in deployment-specific configuration. If the relying party cannot resolve the agent identifier to a trusted public key, it MUST treat the delegator_signature as unverifiable.¶

4.7. Chain Ordering and Integrity

The array MUST be ordered from most recent delegation to earliest:¶

  • Index 0: Most recent delegation (delegator → current token holder)¶
  • Index N: Earliest delegation (first agent after human authorization)¶

This ordering allows efficient validation starting from the immediate delegator.¶

The integrity of the array as a whole is provided by the token-level JWT signature: the signature of the AS that issued the token covers the delegation_chain claim in its exact serialized form, so any modification, removal, reordering, or splicing of records invalidates the token. The integrity of each individual record is provided by its signatures: the delegator_signature, which is REQUIRED on every record, covers the hop's delegator, delegatee, scope, and timestamp, and the as_signature, which is REQUIRED on records created by a foreign AS, covers the same fields with the creating AS's key. The hops are bound into a single path by the continuity rule that record[i].delegatee_id MUST equal record[i-1].delegator_id (Section 8): both identifiers are covered by the respective records' signatures, so a sequence that combines records from different chains fails either signature verification or the continuity check. A chain that fails these checks is invalid, and the Resource Server MUST reject the token with an invalid_delegation_chain error.¶

4.8. Ordering Verification Semantics

The delegation_timestamp field provides ordering evidence for the delegation chain. This section states explicitly which levels of ordering assurance the mechanism provides, and which it does not.¶

  1. Claim-level ordering: Each record's delegation_timestamp is covered by the record's signatures. Monotonicity across the chain (earlier hops carry earlier timestamps) is verifiable by any holder of the token. This is the baseline property this specification provides.¶
  2. Cross-party attestation: Each hop's ordering evidence carries a signature from a party other than the one whose conduct is at issue at that hop: the delegator_signature from the delegating agent, and, on records that cross a domain boundary, the as_signature from the creating Authorization Server. This corresponds to the independently verifiable property discussed for agent action determinability ([I-D.wadkins-agentproto-action-determinability]).¶
  3. Commit-time enforcement is out of scope: Ordering evidence in the token establishes when delegations were recorded, not that preconditions still held at the time the delegated operation was executed. This specification does not claim commit-time or execution-time atomicity. A fresh observation of a valid chain is not a guarantee that the world has not changed between delegation and execution. Deployments requiring such guarantees MUST combine this mechanism with execution-time mechanisms (e.g., conditional requests, resource versioning) or a commitment or reservation protocol.¶

The boundary above is a property, not a mechanism requirement: token-carried evidence records commitments and does not by itself enforce them at execution time. Whatever execution-time mechanism a deployment adds to this specification, the split of responsibilities remains the same: the chain records who delegated what to whom and when; it does not establish that the delegation's preconditions still held at the moment of execution.¶

5.1. Delegation Request

Agent A initiates delegation using OAuth 2.0 Token Exchange [RFC8693]. The request includes delegation-specific parameters to identify the delegatee and the delegated authorization constraints. An example request with a WIT-based agent identity and a scope-based delegation is shown in Appendix B.¶

This specification defines the following extension parameter for use with Token Exchange [RFC8693] requests:¶

delegatee_id:
REQUIRED for delegation requests. A URI identifying the agent receiving the delegated authorization. Implementations SHOULD use a WIT URI when workload identity attestation is available, but MAY use other URI schemes (see Table 1). The AS uses this value to bind the issued token to the delegatee's identity and to populate the delegatee_id field in the delegation_chain record.¶
delegation_proposal:
REQUIRED. A JWS ([RFC7515]) whose payload is the prospective delegation record for this hop: the JSON object containing every field of the final delegation_chain record except the delegator_signature and as_signature fields. The delegating agent signs the canonical serialization (JCS, [RFC8785]) of that object, the same byte string covered by the record signature computation (Section 4), with the private key that the record's delegator_id resolves to. This parameter is the mechanism by which the record's delegator_signature field is produced: upon successful validation, the AS embeds the verified signature into the delegator_signature field of the record it places in the issued token, alongside its own as_signature when the record requires one.¶

Relationship to the actor_token parameter: Token Exchange ([RFC8693], Section 4.4) natively supports delegation through the actor_token parameter: when an actor token is provided, the issued token's act claim identifies the actor; when it is not, the issued token identifies the requesting client as the actor. The delegatee_id parameter serves the delegation scenario in which the delegatee does not yet hold a token or a client identity at the AS, the common case for agent-to-agent delegation, where the delegating agent requests a token bound to a delegatee identified by workload identity. A delegation request MUST NOT include both actor_token and delegatee_id; the AS rejects such a request with invalid_request. When delegatee_id is used, this specification overrides the default actor construction of [RFC8693]: the issued token's act.sub is set to the delegatee identified by delegatee_id, not to the requesting client, and the token is additionally bound to the delegatee's key as defined in the Token Issuance section.¶

The standard and extension parameters in the request are:¶

  • subject_token: Agent A's current access token;¶
  • subject_token_type: urn:ietf:params:oauth:token-type:access_token;¶
  • authorization_details (OPTIONAL) ([RFC9396]): Carries the delegated constraints in a structured format; the structure is deployment-specific and out of scope of this specification. When present, the constraints MUST be equal to or more restrictive than Agent A's authorization. Deployments that do not use structured constraints convey the delegated constraints via scope alone;¶
  • delegatee_id: The agent identifier URI of the delegatee agent (Agent B);¶
  • delegation_proposal: The delegator-signed prospective record for this hop (see above);¶
  • scope (OPTIONAL): Requested scope for the delegated token, which MUST be a subset of Agent A's scope.¶
  • requested_token_type (OPTIONAL): Per [RFC8693], Section 2.1, when this parameter is absent, the issued token type is at the discretion of the Authorization Server, and an opaque access token cannot carry the delegation_chain claim. Implementations using this specification therefore MUST request JWT-format access tokens: the value urn:ietf:params:oauth:token-type:jwt is REQUIRED for requests in which the delegation_chain claim is expected in the response.¶
  • resource (OPTIONAL): The identifier of the target Authorization Server when the delegation crosses a trust domain boundary, as defined in [I-D.ietf-oauth-identity-chaining]. When present, the AS issues a JWT authorization grant suitable for presentation to the target AS instead of a direct access token. Although [RFC8693] permits repeating this parameter, a delegation request MUST NOT include more than one resource value: each delegation hop targets a single trust domain.¶
  • audience (OPTIONAL): A well-known or logical name of the target Authorization Server, as an alternative to resource for cross-domain delegation. One of resource or audience is REQUIRED when the delegation targets an agent in a different trust domain.¶

5.2. AS Validation

The AS MUST perform the following validations:¶

  1. Token Validity: Verify Agent A's token is valid and not revoked.¶
  2. Delegation Permission: Confirm the subject token permits delegation to this delegatee. Permission is determined by AS policy, which MAY be expressed through the may_act claim ([RFC8693], Section 4.1) naming the delegatee, a delegation scope, or another deployment-specific mechanism.¶
  3. Scope Subset: Verify the requested scope is a subset of Agent A's authorized scope (equal to or narrower). Scope expansion is rejected with an invalid_scope error ([RFC6749], Section 5.2); a dedicated error code would not change client behavior here.¶
  4. Structured Constraints (CONDITIONAL): When the request carries structured constraints, verify that they are equal to or more restrictive than Agent A's authorization. The comparison mechanism is defined by the deployment's constraint model and is out of scope of this specification.¶
  5. Delegatee Authentication: Validate Agent B's agent identifier (delegatee_id) to confirm the delegatee is authentic and currently active.¶
  6. Proposal Consistency: Verify the delegation_proposal signature using the public key resolved from the proposed record's delegator_id, confirm that the delegator_id identifies the current holder of the subject token, and confirm that the proposed record is consistent with the request parameters (delegatee_id, scope, and, when present, the constraint references). Reject the request with invalid_request on any mismatch.¶
  7. Chain Depth: Optionally enforce maximum delegation depth, rejecting the request with delegation_depth_exceeded (Section 9.9) when the configured maximum would be exceeded.¶
  8. Upstream Chain Validation (CONDITIONAL): When the subject token contains a delegation_chain claim, verify the chain's continuity, signatures, and scope narrowing as defined in Section 8. If validation fails, reject the request with an invalid_delegation_chain error.¶
  9. Request Freshness: Reject the delegation request if the request time, as observed by the AS, is outside an acceptable time window. A RECOMMENDED maximum skew is 5 minutes. This prevents replay of previously captured delegation requests.¶

5.3. Token Issuance

Upon successful validation, the AS issues a new token for the delegatee with:¶

  • sub: The original user (unchanged)¶
  • act: The delegatee agent's identity, as a single act.sub value without nesting (Section 2.1)¶
  • aud: The audience of the subject token, unless the delegation request constrains it (see below)¶
  • delegation_chain: Extended with a new record for this hop¶
  • scope: The delegated scope (equal to or narrower than the delegator's, as requested)¶

Audience handling: the delegated token's aud is inherited from the subject token unless the delegation request constrains it through the resource or audience parameters of [RFC8693]. Scope narrowing alone does not narrow audience: a delegatee receiving a narrowed scope still obtains a token valid for the same set of Resource Servers, within that narrowed scope. Deployments in which different delegation hops target different Resource Servers SHOULD constrain the audience at each hop.¶

When the AS issues the delegated token at the delegator's request, and the delegatee did not authenticate to the AS for this issuance, the token SHOULD be sender-constrained to the delegatee at issuance. The AS resolves the delegatee_id to a public key (see the Key Resolution section of Section 4) and includes a cnf claim ([RFC7800]) binding the token to the delegatee's key. Two confirmation methods are defined: jkt (the JWK thumbprint defined in [RFC7638]), used with the proof-of-possession protocol of DPoP ([RFC9449]), where the Resource Server verifies the DPoP proof JWT accompanying each request; and x5t#S256, used with mutual TLS client certificate binding ([RFC8705]). The Resource Server MUST verify presenter possession according to the confirmation method indicated by the cnf claim when it is present. Deployments MAY alternatively require the delegatee itself to authenticate and request the delegated token, in which case standard client authentication and sender-constraining apply.¶

Note on DPoP binding: [RFC9449] binds an issued access token to the key that signed the DPoP proof JWT accompanying the token request, normally the requesting client's key. This specification deviates from that model: the delegated token is bound to the delegatee's key, which presents no proof at the token endpoint, and the AS obtains the delegatee's public key by resolving delegatee_id (see Section 4.6). The delegating agent's own DPoP proof, when present, authenticates the request; it does not determine the issued token's key binding. Resource Servers verify the delegatee's DPoP proofs against the cnf claim as usual.¶

6. Chain Extension

When the AS issues a delegated token, it extends the delegation_chain:¶

The delegator's signature over the new record is produced before the request: the delegating agent signs the prospective record and conveys it in the delegation_proposal parameter of the Token Exchange request (Section 5.1); the AS verifies it as part of request validation and embeds it as the record's delegator_signature. The AS applies its own as_signature to the record when the record is created for a token that will be consumed in another trust domain; within a single trust domain, the token-level signature of the issuing AS suffices. The AS propagates the root_authorization_ref claim from the subject token into the issued token unchanged.¶

6.1. Root Authorization Reference Propagation

The root_authorization_ref claim is propagated with the chain: when the AS issues a delegated token within the same trust domain, it copies the claim from the subject token; when the receiving AS of a cross-domain flow issues a local token, it copies the claim from the JWT authorization grant (Section 7). Every token in the lineage therefore anchors to the same root authorization, and a verifier can retrieve the original authorization context through the deployment-specific resolution mechanism of the reference (an audit log query, a consent management API, or, in deployments using a structured authorization evidence model, the root token's evidence claim).¶

7. Cross-Domain Delegation

When delegation hops span multiple trust domains (each with its own Authorization Server), this specification combines the delegation_chain mechanism with the cross-domain transport pattern defined in [I-D.ietf-oauth-identity-chaining].¶

The grant type used for delegation depends on the trust domain boundary:¶

  • Single-domain delegation: Uses OAuth 2.0 Token Exchange ([RFC8693], grant_type=token-exchange) as defined in Section 5. Both delegator and delegatee agents trust the same Authorization Server, which can validate the subject token and issue a delegated token directly.¶
  • Cross-domain delegation: Combines Token Exchange ([RFC8693]) at the originating AS with the JWT Bearer Grant ([RFC7523], grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer) at the receiving AS. When agents belong to different trust domains with different Authorization Servers, the originating AS cannot issue a direct access token for the remote domain. Instead, the delegating agent initiates a Token Exchange request at the originating AS, which returns a signed JWT authorization grant. The delegatee agent then presents this grant to its local AS using the JWT Bearer grant type. The receiving AS verifies the grant using the originating AS's public key (obtained via [RFC8414] metadata) and issues a local access token.¶

7.1. Extension of the JWT Authorization Grant

The JWT authorization grant defined by [I-D.ietf-oauth-identity-chaining] is extended with two claims. The grant MAY carry the delegation_chain and root_authorization_ref claims defined in Section 4. An Authorization Server receiving such a grant MUST process the two claims in accordance with Section 7.3 and MUST preserve them verbatim in the access token it issues, as described in Section 7.5. Everything else about the grant, including its issuance, audience binding, and validation, is defined by [I-D.ietf-oauth-identity-chaining] and is unaffected by this specification. The claims are defined so that they can also be carried by tokens issued without the JWT authorization grant mechanism, for example tokens issued through a direct Token Exchange (Section 5); no validation rule in this specification depends on how the token reached its issuer.¶

7.2. Cross-Domain Delegation Flow

Consider an agent in Trust Domain A that needs to delegate a subset of its authorization to an agent in Trust Domain B:¶

  1. Agent A obtains initial authorization from the user in Trust Domain A (root authorization, no delegation_chain).¶
  2. Agent A initiates a delegation Token Exchange with AS-A, including the resource parameter set to AS-B's identifier (as defined in [I-D.ietf-oauth-identity-chaining]), the delegatee_id parameter identifying Agent B, and the delegation_proposal parameter carrying Agent A's signature over the prospective delegation record. This signals that the delegation targets an agent in Trust Domain B.¶
  3. AS-A validates the delegation, creates a delegation record carrying its as_signature, and returns a JWT authorization grant containing the delegation_chain and root_authorization_ref claims.¶
  4. Agent A transfers the JWT authorization grant to Agent B through an out-of-band mechanism (e.g., a secure internal channel).¶
  5. Agent B presents the JWT authorization grant to AS-B using the JWT Bearer grant type ([RFC7523]), as defined in [I-D.ietf-oauth-identity-chaining], authenticating itself to AS-B with its client credentials or key material. AS-B verifies that the authenticated presenter is the delegatee named by the most recent delegation record of the grant's delegation_chain.¶
  6. AS-B validates the JWT grant signature, verifies the delegation_chain (including AS-A's signature on each record), and confirms policy narrowing constraints.¶
  7. AS-B issues an access token to Agent B for Trust Domain B, preserving the delegation_chain and root_authorization_ref claims from the JWT authorization grant, with act.sub set to Agent B's identifier and, consistent with the Token Issuance section of Section 5, the token sender-constrained to Agent B's key.¶

Agent B then uses the access token to access resources in Trust Domain B. When Agent B delegates further across another trust domain boundary, the pattern repeats; the second hop is shown in Section 7.4.¶

7.3. Cross-Domain Trust Requirements

For cross-domain delegation to function, the following trust requirements MUST be satisfied:¶

  • AS Trust Relationship: Records created by AS-A for a cross-domain delegation carry as_signature (REQUIRED for records created by an AS other than the token's issuer), so AS-B MUST trust AS-A's signing key to verify those records. This trust relationship is typically established through key exchange or by publishing AS-A's public keys via Authorization Server Metadata ([RFC8414]).¶
  • delegation_chain Propagation: AS-B MUST propagate the delegation_chain claim from the JWT authorization grant into the access token it issues, so that Resource Servers in Trust Domain B can validate the full delegation lineage.¶
  • Presenter verification: AS-B MUST authenticate the client presenting the JWT authorization grant and verify that the authenticated presenter is the delegatee named by the most recent delegation record (record[0].delegatee_id). The originating AS SHOULD sender-constrain the grant to the delegatee's key with a cnf claim ([RFC7800]), in which case AS-B verifies the presenter's key against it; where the grant is not constrained, AS-B MUST bind the local access token it issues to the delegatee so that the delegation is usable only by the named delegatee.¶
  • Root Authorization Reference Propagation: AS-B MUST propagate the root_authorization_ref claim from the JWT authorization grant, so that Resource Servers in Trust Domain B can anchor the chain to the original user authorization. Deployments using a structured authorization evidence model MAY additionally propagate the root token's evidence claim, subject to data minimization policies, privacy regulations, or trust agreements between domains; when it is not propagated, the root_authorization_ref value remains the anchor, resolvable through deployment-specific back-channel mechanisms.¶
  • Constraint Enforcement: AS-B MUST enforce that the delegated scope is equal to or narrower than the scope in the JWT authorization grant; scope expansion across domain boundaries is not permitted. When the policy_ref field is present, AS-B relies on the originating AS's issuance-time attestation of the referenced constraints (carried in the record's as_signature), or resolves and compares the references according to its deployment-specific constraint model.¶

7.4. Multi-Domain Chain Extension

When a delegation chain spans multiple domains, each domain's AS may add delegation records to the chain. The cross-domain transport uses the identity chaining pattern (Token Exchange + JWT Bearer Grant) at each domain boundary, while the delegation_chain accumulates records from all domains.¶

A second hop, from Agent B in Trust Domain B to an agent in Trust Domain C, proceeds symmetrically:¶

  1. Agent B initiates a delegation Token Exchange with AS-B, with the resource parameter set to AS-C's identifier, the delegatee_id parameter identifying Agent C, and the delegation_proposal parameter carrying Agent B's signature over the prospective delegation record.¶
  2. AS-B validates the delegation, creates the delegation record for this hop carrying its as_signature, and returns a JWT authorization grant for AS-C whose delegation_chain contains both records (AS-A's record preserved verbatim) and whose root_authorization_ref is propagated from the original authorization.¶
  3. Agent B transfers the JWT authorization grant to Agent C through an out-of-band mechanism.¶
  4. Agent C presents the JWT authorization grant to AS-C using the JWT Bearer grant type ([RFC7523]), authenticating itself to AS-C; AS-C verifies that the authenticated presenter is the delegatee named by the most recent delegation record of the grant's delegation_chain.¶
  5. AS-C validates the JWT grant signature and the full delegation_chain, including the as_signature on each record created by a foreign AS (here, both AS-A's and AS-B's records), and confirms scope narrowing across the whole chain.¶
  6. AS-C issues Agent C a local access token preserving the delegation_chain and root_authorization_ref claims verbatim, with act.sub set to Agent C's identifier and the token sender-constrained to Agent C's key.¶
  7. Agent C presents the access token to RS-C.¶
  8. RS-C validates the delegation_chain as defined in Section 8 and enforces the resulting decision.¶

Resource Servers validating a cross-domain delegation chain MUST:¶

  • Verify the delegator_signature on each delegation record, and the as_signature on each record that carries one, using the signing key of the AS identified by that record's as_id field (which may differ across records);¶
  • Verify trust relationships between all ASes referenced in the chain;¶
  • Verify chain continuity and scope narrowing across domain boundaries;¶

7.5. Claims Transcription for Delegation

Section 2.5 of [I-D.ietf-oauth-identity-chaining] describes Claims Transcription (the process by which Authorization Servers add, change, or remove claims during cross-domain token flows) but leaves the representation of transcribed claims undefined. The delegation_chain claim provides one such representation: when delegation crosses a trust domain boundary, each delegation record captures the transcribed authorization constraints (scope, and when present policy_ref), the identity mapping (delegator and delegatee identifiers), and the cryptographic evidence of the delegating agent (delegator_signature) and of the originating AS that created the record (as_signature).¶

This enables the receiving domain's AS (AS-B) to verify what claims were transcribed, who authorized the transcription, and under what constraints, which addresses the representation gap left by the base identity chaining specification. AS-B SHOULD validate the delegation_chain records from AS-A as part of its Claims Transcription processing before issuing a local access token. In this processing, AS-B preserves the upstream records verbatim: it MUST NOT alter, re-sign, or replace them, and each record's as_id and as_signature remain those of the originating AS; AS-B's own attestation of the transcribed claims is the signature on the local access token it issues.¶

8. Resource Server Validation

Resource Servers validate the delegation_chain as follows:¶

8.1. Signature Verification

For each record in the chain, the Resource Server MUST verify the delegator_signature using the public key of the delegating agent identified by the record's delegator_id field, resolved as described in Section 4.6. A record without a delegator_signature, or with a delegator_signature that does not verify, makes the delegation_chain invalid, and the Resource Server MUST reject the token.¶

When a record was created by an AS other than the AS that issued the token, the record MUST carry an as_signature, and the Resource Server MUST verify it using the public key of the AS identified by the record's as_id field. In single-domain chains, every record is created by the token's issuer, as_id matches the token's iss claim, and the as_signature is typically omitted: the token-level JWT signature already attests to every record in the chain. In cross-domain chains, different records may carry different as_id values, and the Resource Server MUST select the corresponding AS public key for each record. The Resource Server does not need to verify that upstream records' as_id values match the current token's iss claim; the as_id is used solely to select the correct public key for as_signature verification.¶

Signature verification ensures:¶

  • The delegation was authorized by the delegating agent;¶
  • The delegation was witnessed by the originating AS, for records that carry an as_signature;¶
  • The record has not been tampered with.¶

8.2. Root Authorization Anchor

Every token that carries a delegation_chain claim also carries a root_authorization_ref claim, which points to the original authorization event in which the user authorized the root agent. The last record in the chain (highest index) represents the earliest delegation, and its delegator_id identifies the root agent. The authorization of the root agent by the user is not a delegation record and is not represented in the chain; it is anchored by the root_authorization_ref claim.¶

The Resource Server SHOULD verify the root authorization anchor. Since the RS typically observes only the delegated token, it does not have direct access to the original authorization event. The root_authorization_ref value is opaque to this specification; its resolution and validation are deployment-specific. Verification can be performed through one or more of the following means:¶

  • Resolving the root_authorization_ref through deployment-specific mechanisms, for example to a consent record or an audit log entry, and confirming that the referenced authorization event is valid and has not been revoked;¶
  • Using token introspection ([RFC7662]) to confirm that the root agent (identified by the delegator_id of the last chain record) holds a valid, non-revoked root authorization issued by a trusted AS;¶
  • Relying on the structural integrity of the delegation_chain itself: the AS that issued the delegated token has already verified the upstream chain, and the token-level JWT signature covers the entire delegation_chain array, binding the issuance attestation to the token as a whole.¶

If the RS cannot establish confidence in the root authorization anchor through any available mechanism, it SHOULD reject the request.¶

8.3. Delegator and AS Attestations

The two signatures serve distinct purposes and are evaluated independently. The delegator_signature is present on every record: it is the delegating agent's own attestation of the delegation, and it is what prevents a malicious or compromised AS from forging a delegation the delegating agent never made. The as_signature, when present, is the originating AS's attestation that it processed the delegation request, validated the upstream chain, and created the record; it is REQUIRED on records created by an AS other than the AS that issued the token.¶

  • Delegator Signature: Confirms the delegating agent explicitly authorized this delegation, providing non-repudiation of each hop and protection against record forgery by a compromised AS;¶
  • AS Signature: Confirms the originating AS witnessed the delegation and created the record, providing an independent attestation for hops that cross a trust domain boundary.¶

Because the delegator_signature is mandatory, the Resource Server never relies on the issuing AS as the sole attester of a delegation. Every hop carries the delegating agent's own signature, and the AS attestation supplements it exactly where the record's creator is not the token's issuer.¶

8.4. Agent Identifier Status Validation

The Resource Server SHOULD verify the current status of all agent identifiers referenced in the delegation_chain. The verification mechanism depends on the identifier scheme:¶

  • WIT URIs (wit://, spiffe://): Check WIT revocation lists or status endpoints, validate expiration timestamps, or query the issuing identity provider for current status.¶

If any agent identifier in the chain has been revoked or its associated key material has expired, the entire delegation_chain MUST be considered invalid, even if individual records remain cryptographically valid.¶

8.5. Chain Continuity

Verify the chain is continuous:¶

  • For each record at index i (where i > 0), record[i].delegatee_id MUST equal record[i-1].delegator_id, ensuring that the agent who received authorization in one hop is the same agent that delegates in the next hop;¶
  • The delegatee_id of the most recent delegation record (index 0) matches the token's act.sub, and the act claim carries no nested act claim (Section 2.1);¶
  • Timestamps are in descending order: for every record at index i (where i > 0), record[i].delegation_timestamp MUST be less than or equal to record[i-1].delegation_timestamp (two hops within the same second are permitted). When adjacent records carry different as_id values, the verifier SHOULD allow clock skew between the two Authorization Servers (consistent with the freshness window recommended in Section 4) before rejecting on timestamp ordering alone.¶

8.6. Scope and Constraint Validation

Authorization constraints MUST NOT expand along the chain. The constraint data visible to the Resource Server is the per-record scope field and the token's own scope claim; the root boundary (the earliest hop's scope versus the delegator's originally authorized scope) was enforced by the Authorization Server at issuance time and is attested by the record signatures.¶

  • Scope narrowing (MUST): For every record at index i > 0, the set of scope values in record[i].scope MUST be a subset of the set of scope values in record[i+1].scope. The scope of the presented token MUST be a subset of record[0].scope and MUST cover the requested operation. Scope expansion at any hop, or a missing scope field on a multi-record chain, invalidates the chain: the Resource Server MUST reject the token with an invalid_delegation_chain error.¶
  • Structured constraints (CONDITIONAL): When policy_ref is present, the Resource Server relies on the Authorization Server's issuance-time validation of the referenced constraints, attested by as_signature when present and by the token-level signature otherwise. A Resource Server that is able to resolve the reference according to its deployment-specific constraint model MAY additionally evaluate the referenced constraints for the requested operation.¶

When a Resource Server rejects a request because delegation chain validation fails, it responds with HTTP 403 (Forbidden) carrying the error code invalid_delegation_chain, following the error signaling conventions of [RFC6750], Section 3: a WWW-Authenticate header field for bearer token presentation, or the API's own error response body where the API defines one. The error code is the same one registered for token endpoint use in Section 11; its meaning at the Resource Server is specific to delegation chain validation.¶

9. Security Considerations

The security considerations of [RFC8693] and [RFC7519] apply to this specification. The following considerations follow the guidelines in [RFC3552].¶

9.1. Threat Model

This section describes the threat model underlying the delegation_chain mechanism and the security properties it provides.¶

Trusted Entities:¶

  • The Authorization Server (AS) is trusted to correctly validate delegation requests, enforce policy narrowing, and sign delegation records with its private key. The AS is the central trust anchor for the delegation chain.¶
  • The human principal (end user) is trusted to make informed authorization decisions. Whether and how the Authorization Server obtains the user's consent for a delegation is AS policy and is out of scope of this specification.¶

Adversary Capabilities:¶

  • A malicious delegatee agent may attempt to present a token with a forged or truncated delegation_chain to claim authorization it does not possess.¶
  • A malicious delegator agent may attempt to delegate more authorization than it was granted (privilege escalation), or may deny having authorized a delegation (repudiation).¶
  • A compromised AS may attempt to forge delegation records without the delegator's consent. The mandatory delegator_signature on every record mitigates this threat: a forged record does not verify against the delegating agent's key. On records created by a foreign AS, the as_signature provides the additional attestation of the AS that created the record.¶
  • A network attacker may attempt to intercept or modify delegation records in transit. Standard TLS protections apply to all protocol messages.¶
  • A token thief may attempt to steal a delegated access token (e.g., by compromising an agent's storage, intercepting a token in transit, or exploiting a side-channel) and present it to a Resource Server as if it were the legitimate delegatee. The thief may also attempt to replay a previously captured delegation request to obtain a new token.¶
  • A credential thief may attempt to steal an agent's workload identity credentials (e.g., WIT signing key, SPIFFE SVID, or client attestation key material) and impersonate the agent to obtain unauthorized delegations from the AS. This threat is particularly severe in multi-hop chains, where a single compromised agent identity can be used to initiate new delegation paths.¶

Security Objectives: The delegation_chain claim provides the following security properties:¶

  • Integrity: Each delegation record is cryptographically signed by the delegator, and by the AS that created it when the record crosses a trust domain boundary, preventing undetected modification.¶
  • Non-repudiation: The delegator_signature on every record provides independent evidence that the delegation was explicitly authorized by the delegator.¶
  • Scope compliance: Mandatory scope narrowing at each hop prevents privilege escalation through the chain. When the policy_ref field is present, the referenced constraints provide additional fine-grained enforcement attested at issuance time.¶
  • Auditability: The complete chain from the current actor back to the original human principal enables end-to-end audit trail reconstruction.¶

9.2. Privilege Escalation Prevention

The AS MUST ensure that delegation cannot expand privileges:¶

  • Delegated scope MUST be a subset of (equal to or narrower than) delegator's scope;¶
  • Delegation depth MAY be limited;¶
  • Certain scopes MAY be marked non-delegatable.¶

9.3. Chain Integrity

Chain integrity is ensured jointly by the token-level JWT signature, which covers the entire delegation_chain claim in its exact serialized form, and by the per-record delegator_signature, which is REQUIRED on every record. Records created by an AS other than the token's issuer additionally carry that AS's as_signature. These mechanisms enforce chain integrity through the following properties:¶

  • Forgery prevention: Neither a malicious agent nor a compromised AS can forge a delegation record: creating a valid record requires the delegating agent's signature over the record's fields, and a record created by a foreign AS additionally requires that AS's as_signature.¶
  • Tamper detection: Agents cannot modify existing records because any change to the signed fields (including delegator_id, delegatee_id, delegation_timestamp, scope, and policy_ref) invalidates the record's delegator_signature, the as_signature when present, and the token-level JWT signature.¶
  • Record removal detection: Agents cannot remove records from the chain because the token-level JWT signature covers the entire delegation_chain claim as a single unit; any modification to the array length or contents invalidates the token signature.¶
  • Reorder detection: Agents cannot reorder records because the token-level JWT signature covers the delegation_chain array in its exact serialized form; any reordering invalidates the token signature.¶

The four properties above hold for every deployment: the delegator_signature is mandatory on every record, and the token-level signature covers the array as a whole. In single-domain deployments, records typically omit the as_signature, since the token issuer attests to every record through the token-level signature. In cross-domain deployments, the as_signature on foreign records adds independent per-hop attestation that survives token re-issuance.¶

Additionally, the Resource Server SHOULD verify that the delegation_timestamp on each record falls within a reasonable window relative to the token's iat (issued-at) claim. Timestamps that significantly predate the token's issuance or fall in the future may indicate a manipulated or replayed delegation record.¶

9.4. Chain Stripping Prevention

A malicious agent may attempt to present a token with a truncated or empty delegation_chain to hide intermediate delegation hops. For example, an agent holding a token whose chain represents A→B→C (two records: C←B and B←A) could attempt to present only the most recent record [C←B] or an empty chain, thereby concealing the earlier hops from the Resource Server.¶

This attack is prevented by the following mechanisms:¶

  • Token-level signature: The AS signs the entire access token (including the delegation_chain claim) using its private key. Any modification to the delegation_chain claim (including removal of records or replacement with a shorter chain) invalidates the token's signature. The Resource Server MUST reject tokens whose signature does not verify.¶

For opaque (non-JWT) access tokens, the Resource Server MUST use token introspection ([RFC7662]) to retrieve the authoritative delegation_chain from the AS, rather than trusting any client-supplied chain data.¶

9.5. Reordering and Splicing Attacks

Beyond removing records, an attacker holding tokens from multiple delegations may attempt to reorder the records of a chain, or to splice records from two different chains into a new sequence that was never issued by any AS (for example, prefixing a chain with a permissive first hop taken from another user's chain).¶

  • Reordering: The token-level JWT signature covers the array in its exact serialized form, so any reordering invalidates it. Independently, the continuity rule of Section 4.7 fails for a reordered sequence: each record binds its delegator_id and delegatee_id under the delegator's signature, so an attacker cannot rewire a record to a different predecessor or successor.¶
  • Splicing: A spliced sequence combines records that were each individually signed, but into a path that never existed. The token-level signature rejects it outright. If a splice is re-embedded into a newly issued token, which only a malicious or compromised AS can do, the continuity check fails at the splice point unless the AS can also obtain a genuine delegator_signature binding the two chains, and a token that embeds a broken chain is attributable to the AS that issued it.¶

The ordering assurance levels follow Section 4.8: claim-level ordering prevents forgery of a hop's timestamp; cross-party attestation prevents a delegating agent from forging the ordering evidence of its own hop; commit-time enforcement is not provided by this specification and is out of scope. Implementations MUST NOT rely on chain validation in place of execution-time checks.¶

9.6. Policy Reference Substitution

When policy_ref is used, an attacker who can modify a record might substitute the reference to point to different (broader) constraints. This attack is prevented by the record's signatures: the reference is part of the signed field set, so any substitution invalidates the record's delegator_signature, the as_signature when present, and the token-level signature.¶

This specification does not define end-to-end verification of the referenced constraints. A Resource Server that requires such verification resolves the reference according to its deployment-specific constraint model, or relies on the Authorization Server's issuance-time validation attested by the record signatures.¶

9.7. Confidentiality of Delegation Records

A delegation chain may contain privacy-sensitive information and, to prevent disclosure to unintended parties, should only be transmitted over encrypted channels, such as Transport Layer Security (TLS). All claims in a signed but unencrypted JWT (JWS, [RFC7515]) are Base64URL-encoded and readable by any party that obtains the token, including the full delegation topology (all agent identities), policy references (policy_ref), and the authorization event reference (root_authorization_ref).¶

In cases where it is desirable to prevent disclosure of delegation records to unintended parties, the JWT should be encrypted using JWE ([RFC7516]) with nested JWT processing (JWE(JWS(payload))), so that only the intended Resource Server can read the delegation chain contents. In cross-domain deployments, JWE encryption should be used to prevent downstream domains from reading upstream delegation records.¶

Deployments should determine the minimum amount of information necessary for delegation validation and include only such claims in delegation records. The constraints referenced by policy_ref should be scoped to the specific operations being delegated. Agent identifiers (delegator_id, delegatee_id) can be pseudonymous WIT or SPIFFE URIs rather than human-readable names, as described in Section 6.3.1 of the OAuth Assertion Framework ([RFC7521]).¶

The RECOMMENDED short token lifetime (5 to 15 minutes, see Section 9.8) limits the exposure window of any leaked delegation records.¶

9.8. Token Protection

Delegated tokens are subject to replay and theft attacks. The following mitigations address both threats.¶

Sender-constrained tokens: Implementations SHOULD bind issued access tokens to the delegatee's key material using one of the following mechanisms:¶

  • DPoP ([RFC9449]): The delegatee presents a proof-of-possession JWT alongside the access token. The Resource Server verifies that the DPoP proof's jkt thumbprint matches the key binding in the access token.¶
  • Mutual TLS (mTLS, [RFC8705]): The delegatee authenticates using a client certificate; the access token carries an x5t#S256 thumbprint of the certificate, and the certificate is bound to the delegatee_id in the delegation record.¶

When the AS binds the delegated token to the delegatee's key at issuance through a cnf claim ([RFC7800]), as defined in the Token Issuance section of Section 5, the Resource Server verifies presenter possession according to the confirmation method. When sender-constrained tokens are not used, the delegatee_id field alone provides only application-level binding. Deployments that accept this weaker binding SHOULD compensate with shorter token lifetimes and network-level controls.¶

Delegation request replay: An attacker replays a captured Token Exchange request to the AS to obtain a new delegated token. Mitigations include:¶

  • For the initial delegation hop, the AS enforces a freshness window on the subject_token's iat claim (RECOMMENDED skew: 5 minutes);¶
  • Sender-constrained tokens on the delegating agent's access token (e.g., DPoP ([RFC9449]) or mutual TLS) ensure that a replayed request from a different endpoint fails client authentication at the AS;¶
  • TLS protects all protocol messages from on-path capture.¶

Token replay and theft: An attacker presents a stolen delegated token to a Resource Server. Mitigations include:¶

  • Short token lifetimes (RECOMMENDED: 5 to 15 minutes) limit the window during which a stolen or replayed token remains valid;¶
  • Sender-constrained tokens (DPoP or mTLS) ensure that a stolen token cannot be used by a different party;¶
  • Token introspection ([RFC7662]) enables real-time revocation status checking;¶
  • Presenter verification: The Resource Server MUST verify that the presenter's authenticated identity matches delegatee_id of the most recent delegation record (index 0);¶
  • Revocation propagation: When theft is detected, the AS SHOULD revoke the compromised delegation hop, invalidating all downstream tokens (see Section 9.11).¶

Implementations SHOULD use sender-constrained tokens for both the delegation request and the issued delegated token, especially in multi-hop chains where a stolen token could grant access across multiple trust boundaries. The delegation_chain claim additionally enables post-incident forensic analysis by identifying the agents and timestamps at each hop.¶

9.9. Delegation Depth Limits

Implementations SHOULD enforce maximum delegation depth to:¶

  • Prevent unbounded delegation chains;¶
  • Limit token size growth;¶
  • Simplify validation.¶

A RECOMMENDED default maximum depth is 5 hops.¶

When a delegation request would exceed the configured maximum depth, the AS MUST reject the request with an OAuth 2.0 error response using the error code delegation_depth_exceeded and a human-readable error_description indicating the maximum delegation depth has been reached. If a Resource Server receives a token whose delegation_chain length exceeds its locally configured maximum depth, it SHOULD reject the request regardless of signature validity, as excessively deep chains may indicate a misconfigured or malicious delegation path.¶

Implementers should consider the impact of delegation chain depth on token size. Each delegation record typically adds 500 to 1000 bytes to the token payload, including one or two JWS signatures (approximately 200 bytes each for ES256) and, when present, one policy reference per record. A 5-hop delegation chain may therefore add 2.5 to 5 KB to the access token. This can cause issues with:¶

  • HTTP header size limits (commonly 8 KB in default proxy configurations);¶
  • TLS record size constraints;¶
  • Client and server memory consumption during token parsing.¶

To mitigate token size growth, implementations MAY use one or more of the following strategies:¶

  • Short-lived tokens with introspection: Issue access tokens with short expiration and rely on token introspection ([RFC7662]) to retrieve the delegation_chain on demand;¶
  • Policy references: Carry structured constraints by reference (policy_ref) rather than embedding constraint content in the delegation records, as this specification defines.¶

9.10. Cross-Domain Trust

When delegation chains span multiple trust domains, additional security considerations apply:¶

  • AS Key Trust and Record Attribution: Resource Servers in each trust domain must be able to verify as_signature on delegation records issued by Authorization Servers in other trust domains. Delegation records created by an AS in another trust domain MUST carry that AS's as_signature, and Resource Servers MUST verify it. Each delegation record carries an as_id field that identifies the AS that created it, enabling the Resource Server to select the correct public key for signature verification. When delegation records cross a domain boundary, the receiving AS preserves the upstream records with their original as_id and as_signature values intact. To obtain the public key for a given as_id, the Resource Server uses Authorization Server Metadata ([RFC8414]), a shared trust framework, or deployment-specific key exchange. When the receiving AS adds new delegation records to the chain, it signs them with its own signing key and sets as_id to its own identifier. Cross-domain key trust relationships may be established through key exchange agreements, published JWKS endpoints ([RFC8414]), or a shared trust framework. Failure to properly verify cross-domain AS signatures may allow forged delegation records to be accepted.¶
  • Claim Semantics Across Domains: Claims such as sub, scope, and policy identifiers may have different semantics across trust domains. Implementations MUST ensure that claim interpretation is consistent or explicitly mapped at each domain boundary, following the claims transcription guidance in [I-D.ietf-oauth-identity-chaining].¶
  • Revocation Propagation: When the root authorization or any intermediate delegation is revoked, all downstream delegated tokens SHOULD be invalidated. Within a single trust domain, the AS can directly revoke delegated tokens. Across trust domains, implementations SHOULD mitigate the risk of stale delegated tokens through one or more of the following approaches: issuing short-lived delegated tokens to minimize the revocation window, implementing back-channel revocation notifications between ASes (e.g., using Token Revocation [RFC7009] or a proprietary notification mechanism), or requiring Resource Servers in the downstream domain to perform token introspection ([RFC7662]) before accepting delegated tokens.¶
  • Lateral Movement: An attacker who compromises an agent in one trust domain may attempt to use the delegation chain to move laterally to other trust domains. Cross-domain delegation SHOULD be restricted by policy to only the trust domains explicitly authorized by the original user consent.¶

9.11. Delegation Revocation

Revocation of delegated authorization is a critical security operation. This section defines the revocation semantics for delegation chains.¶

Revocation Scopes:¶

  • Root revocation: When the original user revokes the root authorization (the token without a delegation_chain), all downstream delegated tokens derived from that root authorization MUST be considered invalid. Resource Servers validating a delegation chain MUST verify that the root authorization remains valid, either by checking the root token's status directly or by using token introspection ([RFC7662]) on the root token.¶
  • Intermediate hop revocation: When a delegating agent revokes a specific delegation hop (e.g., Agent A revokes its delegation to Agent B), all tokens derived from that delegation (including further downstream delegations such as Agent B to Agent C to Agent D) MUST be considered invalid. Resource Servers SHOULD verify that no delegation record in the chain has been revoked. Within a single trust domain, this can be achieved by introspecting the presented token ([RFC7662]): the AS evaluates the revocation status of each delegation hop of the chain as part of the introspection response, since only the presented token is available to the Resource Server. In cross-domain or high-throughput deployments, performing per-hop introspection may be impractical; in such cases, Resource Servers MAY rely on short token lifetimes combined with back-channel revocation notifications to limit the window during which a revoked delegation remains effective.¶
  • Delegatee token revocation: When a delegatee agent's own token is revoked, only that specific token is affected. The delegation chain record itself remains valid for audit purposes, but the delegatee can no longer use the delegated authorization.¶

Revocation Detection Mechanisms: Resource Servers and downstream Authorization Servers MUST implement at least one of the following mechanisms to detect delegation revocation:¶

  • Short-lived tokens: Issue delegated tokens with short expiration times (e.g., 5 to 15 minutes) to limit the window during which a revoked delegation remains effective;¶
  • Token introspection: Perform token introspection ([RFC7662]) on each token in the delegation chain before accepting the delegated authorization, confirming that no token has been revoked;¶
  • Back-channel revocation notifications: Subscribe to revocation events from upstream Authorization Servers using Token Revocation ([RFC7009]) or a proprietary notification mechanism, enabling proactive invalidation of downstream delegated tokens.¶

10. Privacy Considerations

In addition to the privacy considerations outlined in [RFC8693] and [RFC7519], the following privacy considerations apply to the delegation_chain mechanism defined in this specification.¶

10.1. Data Minimization

The delegation_chain claim carries identity and authorization information about the original user, all intermediate agents, and the delegation policies. As the chain grows with each hop, the amount of information embedded in the token increases. Implementations should apply data minimization principles:¶

  • The constraints referenced by policy_ref should be scoped to the specific operations being delegated, not include broader context about the user's overall authorization.¶
  • Agent identifiers (delegator_id, delegatee_id) should be pseudonymous where possible, avoiding direct exposure of personally identifiable information.¶

10.2. Cross-Domain Information Leakage

When delegation chains cross trust domain boundaries, the delegation_chain claim propagates user and agent identity information from the originating domain to downstream domains. This creates the following privacy risks:¶

  • The sub claim reveals the original user's identity in the originating domain to all downstream domains. Implementations should consider identifier mapping or pairwise pseudonymous identifiers, following the claims transcription guidance in [I-D.ietf-oauth-identity-chaining].¶
  • The root_authorization_ref claim is opaque in this specification, but in deployments where it is resolvable, resolution may expose details of the original consent interaction (e.g., displayed content, session context, channel). ASes should limit who may resolve the reference and should minimize the information returned by resolution.¶
  • The complete delegation chain reveals the full topology of agent relationships, which may be sensitive in competitive or multi-tenant environments.¶

10.3. User Consent Transparency

Whether an Authorization Server requires user consent before authorizing a delegation hop is AS policy and is out of scope of this specification (Section 5). Deployments that do require consent should ensure that the consent interaction clearly communicates:¶

  • The identity of the delegatee agent receiving the delegation;¶
  • The specific operations being delegated;¶
  • Whether the delegation crosses trust domain boundaries;¶
  • The user's ability to revoke the delegation at any time.¶

The root_authorization_ref and policy_ref values are opaque references: the former points to the original user authorization event, the latter to the structured authorization constraints approved for that hop. Neither is resolved or interpreted by this specification. root_authorization_ref is REQUIRED whenever delegation_chain is present; policy_ref MAY be omitted, in which case the delegated authorization is expressed solely by scope.¶

This example is single-domain: both records were created by the AS that issued the token, so the as_signature fields are optional attestations; in a cross-domain token, records created by a foreign AS carry a REQUIRED as_signature from that AS (Section 7). The delegator_signature on each record is computed over the JCS ([RFC8785]) canonical serialization of the record's signed field set; the canonical form and a worked example are given in Appendix C.¶

Appendix D. Validation Checklist

This appendix provides a condensed checklist for implementers. The normative requirements are specified in Section 8 and Section 9; this checklist is informative only.¶

Every token that carries a delegation_chain claim also carries the token-level root_authorization_ref claim. Each delegation record carries a REQUIRED delegator_signature from the delegating agent; records created by an Authorization Server other than the token's issuer additionally carry that AS's as_signature.¶

Token structure:¶

  • iss: Authorization Server identifier¶
  • sub: original user (preserved from root)¶
  • act.sub: delegatee agent identifier¶
  • scope: delegated scope (equal to or narrower than the delegator's)¶
  • root_authorization_ref: reference to the original user authorization event (REQUIRED with delegation_chain)¶
  • delegation_chain: accumulated delegation records¶
  • cnf: delegatee key binding, when the token is sender-constrained ([RFC7800])¶
  • Token signed by AS private key¶

Resource Server validation steps:¶

  1. Verify token-level JWT signature against iss¶
  2. Verify presenter possession when a cnf claim is present, according to the confirmation method (MUST)¶
  3. Verify the delegator_signature on every delegation record, using the delegating agent's key resolved from its delegator_id (MUST; reject with invalid_delegation_chain if missing or invalid)¶
  4. Verify the as_signature on records created by an AS other than the token's issuer, using the key of the AS identified by the record's as_id (MUST)¶
  5. Check chain continuity: record[i].delegatee_id == record[i-1].delegator_id¶
  6. Check that the root_authorization_ref claim is present (MUST) and verify the root authorization anchor as described in Section 8¶
  7. Check act.sub == record[0].delegatee_id, and that act carries no nested act claim (Section 2.1)¶
  8. Check timestamp ordering (descending, within validity)¶
  9. Check scope narrowing (MUST): record[i].scope is a subset of record[i+1].scope for every i > 0, and the token's scope claim is a subset of record[0].scope; treat policy_ref as opaque (narrowing of structured constraints is attested by the AS at issuance time, not verified by the RS)¶
  10. Check agent identifier status (revocation / expiration)¶

Per-hop signing benefits: independent non-repudiation per delegator, flexible per-hop revocation, incremental chain updates, and discrete audit events.¶

Appendix E. Changes from -01 (Informative)

The following substantive changes were made between draft-liu-oauth-chain-delegation-01 and this document:¶

  • Structured constraints carried by reference: The inline delegated_policy object (previously carrying Rego policy content) is replaced by the opaque policy_ref field. The structure and resolution of referenced constraints are deployment-specific and out of scope; the Resource Server treats the value as opaque, and any format defined by a deployment MUST NOT expand the delegator's authorization.¶
  • Two-level scope narrowing: The Authorization Server enforces the narrowing boundary at issuance time (requested scope within delegator scope, rejected with the existing invalid_scope error); the Resource Server verifies only chain-visible data (per-record scope subsets and the token scope claim within record[0].scope). scope is REQUIRED on records of multi-record chains. The policy_expansion_detected error code registration was removed as redundant.¶
  • Token-to-delegatee key binding: At issuance, the AS resolves the delegatee_id to a public key and binds the delegated token to it with a cnf claim ([RFC7800]); the Resource Server MUST verify presenter possession when cnf is present.¶
  • root_authorization_ref as a token-level claim: The per-record root_evidence_ref field of -01 is replaced by a token-level claim, renamed root_authorization_ref, REQUIRED in every token that carries a delegation_chain. The hop in which the user authorized the root agent is not a delegation record; the claim anchors the chain to that authorization event.¶
  • Field rename: The record field delegated_policy_ref of -01 is renamed policy_ref.¶
  • Mandatory delegator signature and scoped AS attestation: The delegator_signature is REQUIRED on every record, and the delegation_proposal request parameter is REQUIRED, so a record without a valid delegator signature is unambiguously invalid. The as_signature is REQUIRED only when the record was created by an AS other than the token's issuer, with as_id REQUIRED whenever as_signature is present. The signed field set is narrowed to delegator_id, delegatee_id, as_id, delegation_timestamp, scope, and, when present, policy_ref.¶
  • Removal of the hash chain, operation_summary, and chain by reference: The prev_record_hash field and the JCS hash-chaining of records are removed; chain integrity now rests on the token-level signature, the per-record signatures, and the continuity rule. The operation_summary field is removed for data minimization. The delegation_chain_ref claim and the chain-by-reference mechanism are removed.¶
  • User interaction mechanism removed: The interaction branch of the delegation Token Exchange flow (the delegation_interaction_required and delegation_interaction_pending errors, interaction_uri, polling, and the interaction_callback_uri parameter) is removed along with its IANA registrations. Whether the AS requires user consent before authorizing a delegation hop is AS policy and is out of scope of this specification.¶
  • Test vectors: The informative test vector now covers the JCS ([RFC8785]) canonicalization of the record's signed field set, over which both signatures are computed.¶
  • RFC 8693 alignment: A delegation request MUST NOT combine delegatee_id with actor_token, and the issued token's act claim is pinned to a single act.sub value without nesting, the actor lineage being carried by delegation_chain. The relationship to the may_act claim and the audience semantics of the delegated token are specified.¶
  • Delegator signature production and cross-domain presenter verification: The delegation_proposal request parameter is defined as the mechanism by which the delegator's signature over the prospective delegation record is conveyed to the AS; the DPoP binding deviation of the delegated token, and the requirement that the receiving AS verify the presenter of a cross-domain JWT authorization grant against the chain's current delegatee, are stated.¶
  • Positioning against ID-JAG: The introduction maps this specification onto the delegation requirements that the Identity Assertion JWT Authorization Grant explicitly leaves open (actor_token processing, authorization propagation across downstream hops, and agent-to-agent delegation), and states where the two specifications compose; the cross-domain section defines the extension of the JWT authorization grant with the delegation_chain and root_authorization_ref claims.¶
  • Editorial: All examples are unified on scope-based delegation records; the informative reference to the Rego-based policy draft was removed.¶
