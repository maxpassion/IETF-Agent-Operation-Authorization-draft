
                    User Consent Extension for JWT Authorization Grant
                      


Abstract

   This document contains early design notes for extending the JWT 
   Authorization Grant to support scenarios requiring explicit user 
   consent before token issuance. These notes informed the development 
   of draft-parecki-oauth-jwt-grant-interaction-response.

1.  Motivation

   The JWT Authorization Grant (RFC 7523) and Identity Assertion Grant 
   (ID-JAG) enable clients to obtain access tokens without direct user 
   approval at the authorization server. However, certain scenarios 
   require explicit user consent:

   o  AI Agent Authorization: Autonomous agents acting on behalf of 
      users need explicit consent for specific operations, not just 
      identity verification.

   o  High-Risk Operations: Financial transactions, data deletion, or 
      other sensitive operations may require step-up consent.

   o  Compliance Requirements: Regulatory frameworks (GDPR, etc.) may 
      require explicit, verifiable consent for certain activities.

   o  Policy-Based Authorization: Fine-grained authorization policies 
      (e.g., "allow purchases up to $50") require user understanding 
      and approval.


2.  Use Cases

   2.1.  AI Agent with Browser Access

      An AI agent needs to perform operations on behalf of a user at a 
      third-party service. The agent can redirect the user's browser to 
      a consent page, then receive a callback when consent is complete.

      This differs from the Device Authorization Grant (RFC 8628) in 
      that no polling is required - the redirect/callback model provides 
      lower latency.

   2.2.  High-Risk Transaction Approval

      A client presents a valid JWT assertion but requests authorization 
      for a high-value financial transaction. The AS determines that 
      step-up consent is required before issuing the token.

   2.3.  Regulatory Compliance

      A client requests access to sensitive data. Regulatory requirements 
      mandate that explicit, auditable consent must be obtained and 
      recorded before access is granted.


3.  Design Considerations

   3.1.  Interaction Response vs Error Response

      Two approaches were considered:

      Option A: Return interaction_required as an error response
         - Pros: Follows existing OAuth error response pattern
         - Cons: Not technically an "error" - more of a flow control

      Option B: Return interaction response as success (200 OK)
         - Pros: Cleaner semantics
         - Cons: Different from typical OAuth patterns

      The final design (draft-parecki-oauth-jwt-grant-interaction-response) 
      chose Option A for consistency with OAuth conventions.

   3.2.  Polling vs Redirect

      Two completion mechanisms are supported:

      Polling: Client periodically re-sends the token request until 
      the interaction is complete. Similar to Device Authorization Grant.

      Redirect: AS redirects to client's redirect_uri when interaction 
      completes. Client then retries the token request. Lower latency.

      Supporting both provides flexibility for different deployment 
      scenarios.

   3.3.  Security Considerations

      o  Interaction URI must be bound to client identity
      o  Sessions must be single-use and short-lived (5 minutes)
      o  HTTPS required for all URIs
      o  State parameter should be used for CSRF protection in redirect

5.  Relationship to Other Specifications

   This extension is designed to work with:

   o  Identity Assertion Grant (ID-JAG): The primary use case for this 
      extension. ID-JAG provides the identity assertion; this extension 
      adds the consent mechanism.

   o  Rich Authorization Requests (RFC 9396): The authorization_details 
      claim can carry structured authorization requests that inform the 
      consent UI.

   o  CIBA (OpenID Connect CIBA): For scenarios where browser redirect 
      is not possible, CIBA can provide out-of-band consent.

   o  Token Introspection (RFC 7662): Consent evidence can be made 
      available through introspection for audit purposes.
